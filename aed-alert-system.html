Audio-Visual Aid for AEDs

An audio-visual alert system for drone-delivered AEDs — Duke University, Pratt School of Engineering

Overview

When someone suffers an out-of-hospital cardiac arrest, applying an automated external defibrillator (AED) within the first five minutes raises the survival rate from roughly 10% to 50%. Rural communities, however, often have no AED nearby, and emergency response times are long. Our client, Dr. Monique Starks, a cardiologist at Duke University, is working to close that gap by delivering AEDs to the scene of a cardiac arrest by drone. A drone can put an AED on the ground quickly, but a bystander still has to find it — in a field, in tall grass, at night, or in the rain.


My team designed and built an audio-visual alert system that attaches to a drone-delivered payload and makes it easy to locate after it lands. The device activates automatically the moment it separates from the drone, flashes a bright multicolored LED strip, and plays a rising sequence of tones from a speaker. When a bystander picks the device up, an accelerometer detects the motion and the device shuts itself off. The work began in Duke's Engineering 101 client design course with Augustus Adams, Beth Lindenbaum, Joshua Stasior, and Nora Taylor, and continued through two semesters of Engineering 102 independent study, where we refined the prototype into a more market-ready device and filed an invention disclosure with Duke's Office for Translation and Commercialization.

Defining the Problem

We started by interviewing our client to understand how the drone-AED system actually works and what it needs from an alert device. The drone hovers and lowers the AED to the ground on a winch from as high as 125 feet, dropping it the last foot or so, and it can land anywhere within roughly a 20–90 foot radius of the target site. Dr. Starks needed a device that would activate on deployment and deactivate once the AED was found, that would survive daily missions outdoors without ever being charged, that would weigh ounces rather than pounds so it would not affect the drone's flight, and that would cost only $20–$40 per unit so it could scale across a fleet. We also had to design for users of all backgrounds, including those with hearing or visual impairments — which is why the device signals both ways rather than choosing one.


We turned those conversations into a weighted set of design criteria using a pairwise comparison chart, which ranked weather resistance first, audio/visual range second, battery life third, cost fourth, and automatic activation last.

Design Process

To get from the problem statement to a design, we decomposed the device into its functions — connection to the AED, audio alert, visual alert, weatherproofing, battery life, automatic activation, and deactivation — and brainstormed options for each. A morph chart combined those options into eleven candidate solutions, which we narrowed with Pugh screening matrices and then a weighted Pugh scoring matrix, using the pairwise ranking of our criteria as the weights.


The winning concept paired an Arduino driving an LED strip and dual-frequency speakers with a magnetically triggered activation system, velcro mounting, reflective material, and a plastic waterproof coating. Building and testing it changed several of those choices: we replaced the magnet with a pull-pin switch and an accelerometer-based shutoff, moved from AA cells to a 9V pack, and swapped the plastic coating for an IP65 project box. The final design keeps the concept — automatic activation, dual-channel alerting, weatherproof housing — with the components that actually survived testing.

Design Solution

Mechanical Activation

A pull-pin switch connects the device to the drone's winch line. When the payload separates from the drone, the pin is pulled and the device powers on with no user interaction required.

Visual Alert

A WS2812B addressable LED strip, driven by the Adafruit NeoPixel library, cycles through red, gold, and blue so the payload is visible from well over 50 feet, day or night.

Audio Alert

A two-wire speaker buzzer sweeps through five octaves of tones. The changing pitch is far easier to localize than a single steady tone, and is audible from over 50 feet away.

Automatic Shutoff

A two-axis accelerometer, read through the Arduino's pulse-width inputs, detects when the device is picked up and turns the alerts off. A five-minute timeout shuts the device down as a backup.

Waterproof Housing

An IP65-rated ABS project box houses the electronics, the 9V battery pack, and the switch, so the device stays functional in rain and wet grass.

Embedded Controller

An Arduino Nano coordinates every subsystem — the light strip, the speaker, the accelerometer, and the activation switch — from a single firmware state machine.

How the Firmware Works

The firmware runs as a two-state machine. In State 1 (alerting), the device drives the LED strip and the speaker together: on each pass through the loop the tone frequency doubles, starting at 110 Hz, while every pixel in the 50-LED strip is set to the color that corresponds to the current step of the sequence. In State 2 (off), the speaker is silenced, the strip is cleared to black, and the enable pin is pulled low.


The device stays quiet about its own motion for the first five seconds after activation, so the shock of landing and the swing of the winch line cannot trigger a false shutoff. After that grace period, every iteration of the alert loop calls updateTriggered(), which reads the accelerometer's X and Y pulse widths. Rather than compare single samples — which proved far too noisy in testing — the routine averages seven readings, waits 30 ms, averages seven more, and compares the two averages. If either axis changes by more than the threshold, the device has been picked up and it switches to State 2. This averaging scheme was the key fix that made the accelerometer reliable; earlier iterations shut the device off spuriously or ignored a real pickup.

Design Criteria and Testing

Visual alert Visible from ≥ 50 feet, success rate ≥ 96% Ask users to walk away until they can no longer see the device, then measure that distance (25 trials). PASS — 25/25 users saw the device from more than 50 feet. Success rate = 100%.
Audio alert Audible from ≥ 50 feet, success rate ≥ 96% Ask users to walk away until they can no longer hear the device, then measure that distance (25 trials). PASS — 25/25 users heard the device from more than 50 feet. Success rate = 100%.
Automatic activation Success rate ≥ 96% Attach the device to a makeshift winch system and drop it from heights of 0–1 feet (30 trials). PASS — the device activated 29/30 times. Success rate = 96.7%.
Water resistance IP rating > 54 Spray the device with a hose on the shower setting from several angles for five minutes to simulate rain (3 trials). PASS — the device remained fully functional 3/3 times, meeting IP55.
Battery life Works in standby for > 281 hours (~12 days) Leave the device powered on and measure the time until the battery is exhausted (3 trials). In progress — motivated our work on Arduino sleep mode and on powering the device from the drone or a rechargeable supply.

Continued Development

After the initial prototype passed its design criteria, we spent two more semesters turning it into something closer to a product. That work included:

  • Researching and testing louder, smaller speakers, including an op-amp-driven speaker circuit, to increase the audible range without growing the enclosure.
  • Migrating from the Arduino Nano to a smaller microchip so the electronics footprint would fit a slimmer, AED-mountable housing.
  • Researching Arduino sleep mode and low-power operation to extend standby battery life toward the 12-day target.
  • Sourcing a more durable, waterproof LED strip after the original strip failed during weather testing.
  • Iterating on the accelerometer firmware across several versions until the averaged, two-window comparison eliminated false triggers.
  • Filing an invention disclosure with Duke's Office for Translation and Commercialization and pursuing a provisional patent, and completing the CITI, LMS, and RCR clinical research trainings required to work with our client's team.

Final Source Code

The complete firmware for the final device is shown below. It was written in C++ for the Arduino Nano and uses the Adafruit NeoPixel library to drive the LED strip. 

                const int LightStringPin = 5;  //pin that connectts to light
const int numLights = 50;      //number of lights in the string
const int speakerPin = 8;      //pin that conects to speaker

unsigned long startTime;
int currentState = 0;
//If currentState = 1 (accelerometer not triggered)
//If currentState = 2 (accelerometer triggered)
unsigned long delayTime = 5000;  //5 seconds

const int xPin = 2;
const int yPin = 3;
const int threshold = 7;

#include <Adafruit_NeoPixel.h>

Adafruit_NeoPixel NeoPixel(numLights, LightStringPin, NEO_GRB + NEO_KHZ800);
bool accelerometerTriggered;

void setup() {
  Serial.begin(9600);

  NeoPixel.begin();
  NeoPixel.setBrightness(100);

  currentState = 1;
  accelerometerTriggered = false;
  startTime = millis();

  pinMode(xPin, INPUT);
  pinMode(yPin, INPUT);
  pinMode(7, OUTPUT);
}

void loop() {
  if ((millis() - startTime) > 300000) {
    currentState = 2;
  }

  if (currentState == 1) {
    int t = 55;  //starting tone for speaker
    digitalWrite(7, HIGH);
    for (int i = 0; i < 5; i++) {
      t = t * 2;
      tone(speakerPin, t, 500);

      //delay + read
      if ((millis() - startTime) >= delayTime)  //once delayTime seconds passes
      {
        //code to read accelerometer and decide whether to turn accelerometerTriggered to true (if it's triggered)
        updateTriggered();

      } else {
        delay(250);  //should be 300, just 200 right now to make difference clear
      }
      if (accelerometerTriggered == true) {
        currentState = 2;
      }

      for (int p = 0; p < numLights; p++) {
        if (i == 0) {
          NeoPixel.setPixelColor(p, NeoPixel.Color(255, 0, 0));
          // NeoPixel.show();
        }
        if (i == 1) {
          NeoPixel.setPixelColor(p, NeoPixel.Color(255, 215, 0));
          // NeoPixel.show();
        }
        if (i == 2) {
          NeoPixel.setPixelColor(p, NeoPixel.Color(0, 0, 255));
          // NeoPixel.show();
        }
        if (i == 3) {
          NeoPixel.setPixelColor(p, NeoPixel.Color(255, 0, 0));
          // NeoPixel.show();
        }
        if (i == 4) {
          NeoPixel.setPixelColor(p, NeoPixel.Color(255, 215, 0));
          // NeoPixel.show();
        }
      }
      NeoPixel.show();
    }
  } else {
    digitalWrite(7, LOW);

    for (int p = 0; p < numLights; p++) {
      NeoPixel.setPixelColor(p, NeoPixel.Color(0, 0, 0));
      NeoPixel.show();
    }
  }
}

void updateTriggered() {  //this method takes ~300 ms
  int x1Total = 0;
  int y1Total = 0;
  int x2Total = 0;
  int y2Total = 0;
  int pulseX, pulseY;
  int accelerationX, accelerationY;
  for (int i = 0; i < 7; i++) {
    pulseX = pulseIn(xPin, HIGH);
    pulseY = pulseIn(yPin, HIGH);
    accelerationX = ((pulseX / 10) - 500);
    accelerationY = ((pulseY / 10) - 500);

    x1Total = x1Total + accelerationX;
    y1Total = y1Total + accelerationY;
  }
  delay(30);
  for (int i = 0; i < 7; i++) {
    pulseX = pulseIn(xPin, HIGH);
    pulseY = pulseIn(yPin, HIGH);
    accelerationX = ((pulseX / 10) - 500);
    accelerationY = ((pulseY / 10) - 500);

    x2Total = x2Total + accelerationX;
    y2Total = y2Total + accelerationY;
  }

  int x1Avg = x1Total / 7;
  int y1Avg = y1Total / 7;

  int x2Avg = x2Total / 7;
  int y2Avg = y2Total / 7;

  if (abs(x1Avg - x2Avg) > threshold) {
    accelerometerTriggered = true;
  }
  if (abs(y1Avg - y2Avg) > threshold) {
    accelerometerTriggered = true;
  }
}
