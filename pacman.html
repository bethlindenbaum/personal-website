FPGA Pac-Man

A hardware implementation of Pac-Man built with Verilog, assembly, an FPGA, and VGA graphics

Created with Sofia Tsvihun for Duke ECE 350

View the source code on GitHub

Overview

FPGA Pac-Man is a playable version of the classic arcade game that my teammate and I designed for Duke's Digital Systems course. Instead of running the game in a conventional software framework, we implemented it on an FPGA using a custom processor, behavioral Verilog, assembly code, register-mapped I/O, and a VGA display.


The finished game contains a complete maze, collectible dots, four animated ghosts, joystick-controlled movement, collision detection, three player lives, a score and high-score system, multiple rounds, and win and loss animations. Pac-Man can move through the maze and its side tunnels while the ghosts follow predefined paths. Eating every dot wins the round, while colliding with a ghost removes one life.

The game rendered on a VGA display, including the maze, dots, Pac-Man, and four animated ghosts.

Gameplay

Joystick Control

A physical joystick connected to the FPGA controls Pac-Man's direction. The most recent requested direction is remembered until Pac-Man reaches a location where that turn is possible.

Maze Boundaries

Movement logic checks the directions available at each position so Pac-Man follows the paths without moving through walls. Side passages wrap Pac-Man to the opposite edge of the maze.

Collectible Dots

Each dot has an individual visibility bit. When Pac-Man's coordinates match a dot's location, assembly code clears that bit and adds ten points to the score.

Four Ghosts

Four independently colored ghosts move around the maze on predefined routes. Each ghost uses a movement counter to determine its current segment and next direction.

Lives and Collisions

Pac-Man begins with three lives. A collision with a ghost pauses play, triggers a flashing animation, removes one life, and resets the character positions.

Scoring and Rounds

Clearing the maze starts another round while preserving the player's score. Losing all three lives resets the game and updates the high score when appropriate.

System Architecture

The project combines a custom processor with dedicated graphics hardware. The processor runs assembly code that manages persistent game state, while the VGA controller handles movement, collision detection, animation, and pixel generation. A modified register file forms the communication boundary between the two systems.

Joystick Up, down, left, and right
→
VGA Controller Movement, sprites, collisions, and animation
↔
Register-Mapped I/O Coordinates, lives, win state, and dots
↔
Custom Processor Assembly game loop and dot state
→
VGA Display Real-time game output

Register-Mapped I/O

We connected the processor and graphics logic by extending the processor's register file with dedicated hardware inputs and outputs. This allowed the assembly program and VGA controller to share state without adding new instructions to the processor.

Shared State Direction Purpose
Pac-Man X and Y Graphics to processor Lets the assembly program determine whether Pac-Man is currently positioned over a dot.
Number of lives Graphics to processor Tells the assembly program when a complete game reset is required.
Game-win signal Graphics to processor Causes the dot registers to be reinitialized after the player clears the maze.
Dot visibility registers Processor to graphics Controls which dots the VGA controller draws in each row of the maze.

Assembly Game State

Twenty-one processor registers store the maze's dot state, with each bit representing one dot. At startup, the assembly program fills those registers with ones. During the game loop, it compares Pac-Man's hardware-provided coordinates with the stored dot locations and clears the matching bit using a bit mask. 

# Registers $3 through $23 hold dot visibility by row.

initialize:
    addi $3, $0, -1
    addi $4, $0, -1
    addi $5, $0, -1
    # Additional rows are initialized in the same way.

game_loop:
row1:
    lw   $24, 40($0)       # Load row 1's y-coordinate.
    bne  $24, $2, row2     # Continue if Pac-Man is elsewhere.

col1:
    lw   $24, 9($0)        # Load the dot's x-coordinate.
    bne  $24, $1, col2

    addi $29, $0, -3       # Mask with one cleared bit.
    and  $3, $3, $29       # Mark the dot as eaten.
    j    score

Graphics and Animation

The VGA controller generates the maze and sprites in real time. Sprite artwork is stored in memory files, and the active pixel location selects the corresponding sprite data and output color. Counters update character movement at a playable speed without changing the VGA timing rate.

Pac-Man Animation

Pac-Man alternates between a closed-mouth sprite and an open-mouth sprite oriented up, down, left, or right based on the current direction of travel.

Ghost Animation

The ghosts alternate between two sprite frames, producing the characteristic squiggling motion at the bottom of each character.

Life-Loss Animation

After a collision, Pac-Man flashes three times while the ghosts temporarily disappear and movement pauses before the round resumes.

Win Animation

After all dots have been eaten, the maze walls flash in a different color three times before the next round begins.

Timing Challenges

One of the most difficult parts of the project was synchronizing the processor and graphics hardware. Initially, the processor and VGA controller generated separate 25 MHz clocks from the FPGA's 100 MHz system clock. Small differences between those clock domains caused sprites to become pixelated and occasionally caused the processor to miss reset signals.


We corrected the problem by generating a consistent 25 MHz clock with a phase-locked loop and supplying the same clock to both systems. This substantially improved the graphics and made the round-reset, game-reset, and game-win communication reliable.

High-Score Timing

Updating the high score introduced another hardware timing issue. On a game loss, the design needed to compare the final game score with the high score during the same transition that reset the game score to zero. Depending on signal timing, the high-score logic could see the reset value instead of the completed score.


We resolved this by adding a delayed score register that preserved the previous game's value for one additional clock cycle. The high-score logic reads this stable delayed value while the current game score is reset.

Testing

We tested the project directly on the FPGA by playing through every major game state: eating individual dots, clearing the entire maze, colliding with each ghost, losing one or more lives, losing a full game, beginning another round, and replacing the high score. On-board LEDs exposed internal values during debugging, and other people play-tested the game to uncover interaction bugs we might not encounter ourselves.

Built With

  • Verilog — VGA graphics, movement, collision detection, animation, score calculation, resets, and processor hardware.
  • Assembly — dot-state initialization, coordinate comparisons, bit-mask updates, and game-state handling.
  • Custom 32-bit processor — executed the assembly game loop and communicated with the graphics hardware through its register file.
  • FPGA development board — hosted the processor, graphics pipeline, memories, clocking logic, and physical input/output.
  • VGA — displayed the maze, sprites, dots, lives, score, high score, and animations.
  • Physical joystick — supplied active-low directional inputs through a pull-up resistor network.
  • Python — converted image and color data into memory files used by the graphics hardware.

Possible Next Steps

Future additions could include dynamic ghost behavior, ghosts that chase Pac-Man, power pellets, edible ghost states, sound effects, bonus items, and Duke or ECE-themed Easter eggs such as a Duke “D” or a NAND gate.
